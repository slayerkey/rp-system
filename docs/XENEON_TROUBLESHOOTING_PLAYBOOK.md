# XENEON Troubleshooting Playbook

This is the durable PackRat recovery guide for CORSAIR iCUE / XENEON Edge widgets.

Use it when a widget works in a browser but fails in iCUE, receives Marketplace review feedback, behaves differently on a tester's physical XENEON Edge, or repeatedly needs product-specific fixes for the same class of problem.

The goal is to turn every hard-won fix into shared infrastructure or a regression test so future products inherit it automatically.

## Core rule

Reproduce first. Classify second. Fix the root cause third. Add a regression fourth.

Do not begin by rewriting the product.

If several products can fail the same way, inspect shared RatPack tooling before adding a product-local workaround.

## Confidence ladder

A green result at one layer does not prove the next layer.

Use this order from lowest to highest confidence:

1. authored-source browser fixtures
2. generated shipping HTML
3. exact extracted official package
4. lexical iCUE binding smoke
5. no-callback autosync smoke
6. Corsair Labs Windows compatibility runner
7. StreamSpell packaged preview
8. real iCUE
9. physical XENEON Edge

Physical hardware is not required for release-candidate status when the applicable automated gates pass.

Do not claim physical-device verification when it did not happen.

When real iCUE or a physical XENEON contradicts a browser, runner or preview, the real-host observation wins.

## Recovery procedure

For every bug or rejection:

1. record the exact product slug and version
2. preserve the exact package that failed when available
3. record slot size/orientation, settings and iCUE version
4. write the smallest reproducible fixture
5. classify the failure
6. inspect shared infrastructure
7. fix the smallest root cause
8. regenerate the shipping widget
9. rerun the closest failing layer
10. rerun the complete applicable release gate
11. add a regression before closing the issue

For Marketplace rejections, also preserve the rejected version unless the Marketplace explicitly requires a version change.

## Failure families

### 1. iCUE lifecycle and settings

Real iCUE properties are document-level JavaScript bindings. They are not guaranteed to be normal own properties of `window` or `globalThis`.

PackRat shipping output must preserve the canonical bridge generated by `tools/xeneon/inline.py`:

- `__ratpackIcueRead`
- `__ratpackIcueBindingBridge`
- `__ratpackIcueSyncGlobals`
- `__ratpackIcueBindingSync`

Do not replace the bridge with a product-local mock or dynamic eval-based lookup.

Settings-backed widgets should route initialization and settings changes into one idempotent refresh path. Register both `icueEvents.onICUEInitialized` and `icueEvents.onDataUpdated` when the widget uses those lifecycle events.

Test two update paths:

- explicit `onDataUpdated`
- bindings change with no callback, verified by the autosync smoke

A browser harness that assigns settings onto `window` can hide the exact failure that real iCUE exposes.

### 2. Stale source versus package

The authored source under `widgets/_src/<slug>/` is canonical.

The shipping `widgets/<slug>/index.html` is generated.

Before debugging host behavior, regenerate with `tools/xeneon/inline.py` and fail if `--check` says the shipping file is stale.

After official packaging, downstream tests must consume the exact package or exact extracted package. Do not rebuild between validation layers.

### 3. Property metadata

Vendor CLI success is necessary but not sufficient.

Real iCUE has rejected metadata shapes that looser environments accepted.

Use current CORSAIR control metadata. In particular:

- do not invent `data-options` where `data-values` is required
- keep Custom Style controls together and ordered `textColor`, `accentColor`, `backgroundColor`
- keep `sensors-factory` defaults aligned with the documented sensor expression, not a runtime-shaped placeholder
- keep settings groups reachable in the real iCUE settings viewport

If a real importer rejects a control, add an exact-package regression for that metadata shape.

### 4. Network and file-origin behavior

Imported widgets run from a local `file://` origin.

Do not assume a third-party API allows readable cross-origin responses.

For timing or reachability only, a tested opaque request may be valid. Label it honestly as HTTPS response timing, not ICMP ping.

For readable response bodies or throughput, use an endpoint that explicitly permits the required cross-origin path or a deliberate local companion.

Every network product must have deliberate visual states. Use product-appropriate equivalents of:

- LOADING
- NO CONNECTION
- API OFFLINE
- BAD RESPONSE
- RATE LIMITED
- NO DATA

Test timeout, malformed data, offline, recovery, rate limit and reconnect.

A handled network failure must never leave a blank widget.

### 5. Providers

Do not let one unavailable provider prevent the rest of the interface from starting unless that provider is truly required for the entire product.

For each provider, test:

- loading
- normal data
- empty data
- unavailable
- stale
- error
- recovery

Fixtures may simulate valid provider responses only. They must not imply shipping fields or capabilities the provider does not expose.

### 6. Persistence

Parse local storage defensively.

Test:

- first run
- normal reload
- old schema where applicable
- malformed/corrupt stored JSON
- missing fields
- reset/clear behavior

Version persisted data when the structure can change.

A bad persisted value should fall back safely instead of preventing startup.

### 7. Timers, subscriptions and cleanup

Repeated lifecycle calls must not create duplicate intervals, duplicate listeners or duplicate provider loops.

Keep one owner for each timer/subscription.

Make initialization idempotent.

Clean up on `pagehide` or the appropriate lifecycle boundary.

Test re-entry, settings refresh, reconnect and long-running behavior.

### 8. Touch and interaction

Treat every layout as a touch surface, not just a screenshot.

Test:

- visible touch target size
- rapid repeated taps
- disabled states
- active states
- accidental double actions
- destructive controls
- confirmation flows
- disconnected controls

Closing windows, stopping streams, clearing history or similarly destructive actions should require deliberate confirmation when accidental taps would be costly.

### 9. Responsive layout and typography

Test all eight official XENEON size/orientation compositions.

Also inspect native wide layouts such as 1688x696 and/or 2536x696 when information density matters.

Test:

- overflow
- clipping
- descenders
- long titles
- long device/app names
- Unicode
- HTML-looking text
- empty values
- maximum card/list counts
- settings overlays
- error banners
- touch controls

Do not judge readability only from the iCUE preview.

### 10. User-provided text

Render user content as text unless HTML is explicitly required and safely sanitized.

Fixtures should include strings such as:

`<b>not markup</b>`

and Unicode/emoji samples.

Long values should wrap, truncate or scroll deliberately rather than break the layout.

### 11. Local companions

Use a companion only when the XENEON web runtime cannot reliably perform the required native or network action.

A PackRat companion should be the smallest local bridge that solves the missing capability.

Prefer:

- localhost only
- no PackRat cloud
- no secret collection
- explicit health/version handshake
- reconnect behavior
- deliberate disconnected UI
- narrow commands and normalized state
- no logging of sensitive clipboard, token or account contents
- one per-user running instance, with a clean way to exit before updating
- reusable long-lived HTTP clients for polling/control providers instead of creating a new client for every request
- explicit pair, unpair, disconnect, clear-key and cache-reset paths when credentials or local pairings can go stale
- bounded discovery and polling cadence; an empty device list must not cause aggressive multicast/network discovery forever
- provider reachability derived from the provider's real connectivity resources rather than assuming every normalized device is online
- independent LAN/cloud/provider failure domains where one optional transport should not disable a working one
- a stable customer-accessible companion download URL when the `.icuewidget` cannot contain the native companion

Test the widget with the companion healthy, unavailable, restarting, version-mismatched and already running when launched a second time.

For Windows GUI/tray companions, do not treat a GitHub-hosted Windows runner as proof that the production desktop UI path works. Hosted runners execute in a non-interactive service session. A useful hardware-free split is:

- launch the exact published customer executable normally and prove its production bootstrap side effects, such as per-user install location and startup registration
- use a deliberately narrow headless CI mode only to prove the exact installed binary's localhost transport and process lifecycle when a desktop is unavailable
- keep tray UI, clipboard listener and physical-device behavior outside the claims of that headless gate

Windows process and filesystem teardown also need explicit testing:

- before replacing a running installed executable, stop the exact installed process and wait for it to exit before overwriting the binary
- before deleting an install/data directory, wait for the process to exit and retry deletion for transient executable/state-file locks
- never suppress a final cleanup failure; fail visibly if the install directory or startup registration remains
- execute the uninstaller from the exact customer release ZIP rather than a cleaner source-tree copy

For companion-backed Marketplace products, also test the customer dependency path itself:

- the Marketplace description clearly says a companion is required
- the dependency has a stable link, not a temporary Actions artifact
- the widget's offline/setup state tells the customer where to download it
- the download resolves without GitHub authentication or a PackRat account
- the release ZIP contains the executable plus setup/recovery instructions
- updating the companion does not require Task Manager or deleting local app data
- removing credentials removes stale cloud-only/device state without breaking unrelated local transports

### 12. External tester or physical-device reports

When a tester reports a real XENEON issue, collect:

- exact package/version
- iCUE version
- slot and orientation
- screenshot/video if useful
- settings values
- exact steps
- whether restart/reload changes the behavior

Do not dismiss a physical failure because browser CI is green.

Reproduce the closest equivalent automatically, fix it, then add a regression for the discovered mismatch.

## Release-candidate gate without owned hardware

A hardware-free XENEON release candidate should complete all applicable layers:

- canonical source and structure QA
- deterministic fixtures
- all eight layouts
- interaction and state testing
- generated shipping HTML freshness check
- official CORSAIR validation
- official `.icuewidget` package
- exact ZIP/package integrity
- lexical settings regression when properties are declared
- autosync regression when live setting latency matters
- Corsair Labs Windows runner
- StreamSpell packaged verification
- deterministic Rat Art from real widget captures
- Rat Ship marketplace kit
- stable dependency/download path for any required external companion
- companion install, update, reset and single-instance behavior when a native bridge is required

Record any remaining real-iCUE or physical-device uncertainty. Do not convert uncertainty into a fake blocker when all automatable evidence is green.

## Rejection matrix template

For a multi-product rejection or tester batch, make a table before patching:

| Product | Version | Symptom | Failure family | Shared or local | Reproduced | Regression added | Status |
|---|---|---|---|---|---|---|---|

Group the rows by root cause.

One shared fix with regressions is better than ten slightly different local patches.

## Definition of recovered

A bug is not recovered merely because the screenshot looks correct.

Recovered means:

1. root cause understood
2. canonical source fixed
3. shipping artifact regenerated
4. failing layer passes
5. nearby failure states still pass
6. exact package passes applicable downstream gates
7. regression prevents recurrence
8. physical uncertainty is stated honestly when hardware was not used
